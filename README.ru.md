# E2E Console

Локальная страница для E2E-прогонов мобильного приложения на эмуляторе, телефоне или iOS-симуляторе:
сценарии в YAML, скриншоты по шагам, проверки бэкенда от нескольких аккаунтов, запросы приложения
и логи бэкенда по шагам, сверка с макетами Figma и с эталонными скриншотами, очередь на несколько
устройств. Экран ведёт свой драйвер на adb или Maestro.

Ничего не знает о конкретном приложении: пакет, стенд, вход в аккаунт, конверт запросов и логи —
настройки и плагины. Свой проект удобно держать пресетом: один YAML с настройками, блоками и
сценариями (см. «Пресеты»).

## Запуск

```bash
npm install
node server.js
```

Открыть http://localhost:4777. Пустая консоль открывается на странице **«Как начать»** (`#/start`, есть и в шапке):
живой чеклист из пяти шагов — adb и emulator найдены, устройство подключено (запуск эмулятора по AVD или «+ телефон»),
приложение известно (кнопка «Взять с экрана устройства» заполняет пакет и activity по тому, что открыто на
устройстве; путь к APK и «Установить APK»), бэкенд по желанию (API, роли, плагин входа), первый сценарий
(создать или импортировать пресет). Та же кнопка «Взять с экрана» есть в «Настройках». Нужны Node 20+ и
Android SDK (adb, emulator). Консоль ищет SDK сама: `ANDROID_HOME` → `ANDROID_SDK_ROOT` → стандартная папка
системы (`%LOCALAPPDATA%AndroidSdk`, `~/Library/Android/sdk`, `~/Android/Sdk`) → `adb` и `emulator` из PATH;
свой путь задаётся в настройках (`adbPath`, `emulatorPath`). Для движка Maestro — Maestro CLI
(`~/.maestro/maestro/bin` или PATH) и Java 17+ (консоль ищет её в `~/.gradle/jdks`, в Android Studio и в
системных папках JDK на macOS и Linux). Движок «свой (adb)» — собственный драйвер консоли поверх adb.
Основная проверка шла на Windows; на macOS и Linux пути и поиск написаны, но на живой машине не прогонялись.

## Язык сценариев

Сценарий — YAML (в редакторе есть режим «YAML», форма — для простых правок). Шаги коротко
(`- tap: Каталог`) или с полями. Полный пример — `examples/scenario-advanced.yaml`, схема для
редактора — `schema/scenario.schema.json` (и `GET /api/schema`).

```yaml
name: Заказ с доставкой
vars: { product: demo-123 }
setup:                                   # первым; упал — основные шаги не идут
  - use: reset-cart
steps:
  - use: add-to-cart                     # блок с параметрами
    with: { product: "{{product}}" }
  - use: checkout
  - if: { visible: Указать данные }    # условие проверяется один раз, когда дошли
    then: [ { tap: Указать данные } ]
    else: [ { assertText: Главная улица } ]
  - repeat:                              # пока не станет / не больше N раз
      until: { notVisible: Оплата проверяется }
      max: 20
      steps: [ { wait: 2 } ]
  - api: { url: api/v1/orders, poll: 40, expectPath: items.0.status, expectValue: paid, save: { orderId: items.0.id } }
  - api: { url: "api/v1/courier/{{orderId}}/pickup", method: POST, auth: courier }
teardown:                                # всегда, кроме «Остановить»
  - api: { url: api/v1/cart/clear, method: POST }
matrix: { delivery: [Курьер, Самовывоз] }   # один сценарий × строки = несколько прогонов
rules: { noServerErrors: true }            # любой 5xx у приложения — прогон упал
```

| Что | Как пишется |
|---|---|
| Блоки | `blocks:` в сценарии или общая библиотека (`data/blocks/*.yaml`, «Настройки → Библиотека блоков»); `- use: имя`, `with: {…}`; `params: [a, b]` или `params: { a: значение по умолчанию }` |
| Фазы | `setup`, `steps`, `teardown` — teardown выполняется и после падения |
| Условия | `- if: {…} then: […] else: […]`; на любом шаге `when: {…}`, в том числе на `repeat`, `use` и внутри них; вложенные условия складываются (шаг идёт, только если верны все). Условие: `visible`, `notVisible`, `var` (+ `equals` / `matches`), `platform`, `not`; неизвестный ключ — ошибка линтера |
| Повтор | `- repeat: { until: {…} \| times: N, max: N, steps: […] }` |
| Опрос API | `poll: 60` — повторять запрос, пока `expectPath`/`save` не сойдутся. GET опрашивается и без `poll`, а POST/PUT/PATCH/DELETE уходят один раз, пока `poll` не задан явно |
| Матрица | `matrix: { a: [1, 2], b: [x] }` (все сочетания) или список строк; переменные строки — `{{a}}` |
| Роли | `auth: <роль>` на API-шаге; роли и их токены/номера — в настройках (`accounts`), по умолчанию — аккаунт самого приложения (`auth.appAccount`), иначе первая роль в таблице, `none` — без токена; в шагах есть `{{роль.phone}}` |
| Проверки экрана | `assertText: { text, absent, regex, count, id }`; `assertScreen: { baseline, threshold }` — сравнение с эталонным скриншотом (первый прогон сохраняет эталон в `data/baselines`, на странице прогона можно принять новый) |
| Политика шага | на любом шаге: `retry: N`, `optional: true` (неудача не роняет прогон, шаг «с оговоркой»), `flaky: true` (две попытки и пометка), `timeout`, `screenshot: false` |
| Платформы | `target: { android: Назад, ios: Back }` (так же `text`, `url`); `when: { platform: ios }` |
| Подстановки | переменные настроек и сценария, `save` из API-шагов, `{{uuid}}`, `{{now}}`, `{{hex64}}`, шаблоны из настроек (`{{context}}`) |
| Замер | `measure: true` или `measure: { iterations: 3, flashlight: false }` — кадры, CPU и память на каждом экранном шаге, балл за прогон; см. «Производительность» |
| Прокрутка | `swipe: { direction, fast: true, times: 10, pause, duration }` — `fast` резкий флинг (80 мс почти на весь экран), `times` серия подряд: нагрузочный тест списка |
| Раздел | `section: Каталог` — куда сценарий попадает в истории производительности; без него — «Прочее» |
| Варианты | `variants: { lite: { title, vars, setup, teardown } }` — один прогон на вариант; `setup` варианта идёт перед сценарием, `teardown` после, `vars` доступны как `{{…}}`; история считает варианты отдельно |
| Вкладки | на главной две вкладки: сценарии с `measure` или тегом `perf` — во вкладке «Нагрузка», без `measure` или с тегом `tests` — во вкладке «Тесты» (один сценарий может быть в обеих); из «Нагрузки» запуск всегда с замером, «Замерить всё» ставит в очередь всю вкладку |

**Проверка до запуска.** Линтер (при сохранении, `GET /api/scenarios/<id>/lint`, `node tools/e2e.js lint all`)
ловит неизвестные поля и типы, незаданные переменные, несуществующие блоки и роли, а по последнему прогону —
поля `save`/`expectPath`, которых не было в ответе. С ошибками сценарий не запускается (`?force=1` — всё равно).

## Производительность

`measure: true` в сценарии (или кнопка «⏱» у сценария, `--measure` в командной строке) включает замер вокруг
каждого экранного шага — Android, движок adb или Maestro. Ничего не нужно добавлять в приложение: консоль
читает счётчики самой системы через adb.

| Что | Откуда | Зачем |
|---|---|---|
| **Стоимость кадра** p50 / p95 | `dumpsys gfxinfo framestats`: UI-поток (ввод, анимация, layout, запись рисования) + RenderThread без ожидания буфера | сколько процессорного времени приложение тратит на кадр — число, которое переносится с эмулятора на телефоны |
| **Jank** | доля кадров дороже кадра 60 fps (16,7 мс) — одна мерка для всех устройств; рядом `jankHz` — дороже реального интервала экрана (на 120 Гц это 8,3 мс) | «дёргается ли» |
| **На экране** p95 · пропущено | тот же framestats: от vsync до показа, доля пропущенных дедлайнов | как это выглядело на этом устройстве; на эмуляторе упирается в видеопуть хоста, поэтому в балл не входит |
| **Старт** | `am start -W` TotalTime | холодный старт: процесс → первый кадр, мерит сам Android |
| **Переход** | от кадра, обработавшего нажатие, до конца первой серии кадров | сколько экран «ехал» после тапа или свайпа |
| **CPU · RAM** | `/proc/<pid>/task/*/stat`, `/proc/<pid>/statm` до и после шага | процессор в долях одного ядра, кто из потоков ел; RSS |
| **Flashlight** | профайлер [bamlab/flashlight](https://github.com/bamlab/flashlight) рядом: CPU по потокам, FPS из atrace, RAM | независимый балл 0–100 по их формуле |

**Балл 0–100** (за прогон — по шагам основной фазы, setup/teardown не считаются): половина — доля jank
(0 % → 100, 30 % → 0), половина — p95 стоимости кадра (≤ 8 мс → 100, ≥ 33 мс → 0). ≥ 85 «плавно»,
≥ 60 «нормально», ниже — «тормозит». Балл говорит об устройстве, на котором шёл прогон; меньше 20 кадров —
балла нет. Главная ценность — история: на странице прогона таблица по сборкам — медиана замеров сценария
на каждой сборке и разброс (мин–макс). Один замер ничего не доказывает: шум между прогонами — 4–13 баллов
на телефоне и до 34 на эмуляторе, поэтому разница меньше разброса показывается серым «в шуме», а сравнение
с единственным замером — «1 замер». Цветная Δ появляется только когда изменение больше разброса.

`measure: { iterations: 3 }` ставит в очередь три прогона подряд — медиана по ним и попадает в таблицу
сборок. Для сравнения сборок нужно 3–5 итераций на каждую, иначе разница утонет в шуме. Серия замера всегда идёт на одно устройство: при «любом свободном» оно выбирается в момент запуска, а не
по мере освобождения очереди, чтобы итерации одной серии не разъехались по эмулятору и телефону. Во вкладке
«Нагрузка» у сценария с вариантами — подстрока на каждый вариант со своим последним замером, баллом и «⏱». `flashlight: false` отключает профайлер Flashlight (он ставится `npm install`'ом как
`@perf-profiler/profiler`, кладёт свой бинарник в `/data/local/tmp` устройства и работает целиком
локально — ничего никуда не отправляется; команда `flashlight cloud` консолью не используется).

Что не измеряется: iOS (пока), GPU-нагрузка на эмуляторе (видеокарта хоста), нагрев. Один и тот же
образ эмулятора и тихий хост — иначе цифры плывут; сравнивайте сборки, а не абсолютные числа.

**Гигиена эмулятора** (проверено 2026-11-09 на эмуляторе Android 16): после суток аптайма со снапшотами
эмулятор рисовал 5–13 кадров на свайп при стоимости кадра 110–200 мс; после `adb emu kill` и холодного старта
`emulator -avd <avd> -no-snapshot-load` — 55–75 кадров на свайп и p50 7,6 мс на той же сборке. Перед серией
замеров: холодный старт, минуту подождать после загрузки (стартовые сервисы), `adb shell cat /proc/loadavg` ниже ~4,
на хосте не идут сборки, индексация, Defender и обновления. `android.hardware.radio-service.ranchu`, съедающий целое
ядро, — баг самого эмулятора: авиарежим и `gsm off` его не унимают, помогает только `adb root` + `stop vendor.radio-ranchu`
(приложение и Wi-Fi при этом работают). Для этого на странице «+ телефон» у эмулятора есть кнопка «Подготовить к
замеру»: `adb root`, команды из настройки `emulatorHygiene` (по одной в строке), затем load average и top гостя.

**История и баллы.** «История» в шапке (`#/perf`, данные — `GET /api/perf/summary`): по каждому устройству
(эмулятор, каждый телефон) и сборке — итог «N из M», как у бенчмарков: балл сценария (и варианта) — медиана его
прошедших замеров на этой сборке, балл раздела (`section`) — среднее по его сценариям, итого — сумма разделов, так
что максимум растёт с числом разделов, а слабый раздел виден как дыра, а не размазывается по среднему. Ниже —
таблица по сборкам с баллами разделов и Δ к предыдущей сборке на этом устройстве: регрессия видна в столбце. Блок
«Сравнение сборок» ставит рядом выбранную сборку и базу (по умолчанию предыдущую): итог, разделы и каждый сценарий —
балл, p95, jank, старт, с разницей и пометками «новый» / «не мерялся». Δ итога считается только по разделам, которые
есть в обеих сборках (иначе рядом стоит ≠), чтобы добавленный раздел не выглядел регрессией. Каждая строка ведёт на отчёт прогона и умеет
замерить сценарий (или конкретный вариант) ещё раз. Сравнивать имеет смысл только в пределах одного устройства и
одного режима Flashlight. Рядом с медианами стоит разброс, Δ внутри разброса помечается «в шуме». Сборка — это
versionName + versionCode + md5 установленного APK (снимается с устройства, около секунды на прогон); прогоны,
записанные до 2026-11-11, группируются по имени файла APK, поэтому первый новый замер старой сборки начнёт
новую строку. Прогоны без отметки формулы балла пересчитываются по сохранённой статистике кадров и помечены «*».

**Телефон и калибровка.** «+ телефон» в шапке — страница подключения по Wi-Fi (Android 11+): код
сопряжения из окна «Беспроводная отладка» и адрес; порт подключения консоль ищет сама через mDNS,
телефон запоминается в `devices`. Прогони на телефоне тот же перф-сценарий с замером и нажми на его
странице «Сделать эталоном калибровки»: консоль берёт эмуляторный прогон того же сценария, того же варианта
и той же установленной сборки (и того же режима Flashlight, если есть), считает K = p95 стоимости кадра на телефоне ÷ на эмуляторе (медиана по шагам), узнаёт
чип телефона (`ro.soc.model` → `lib/chips.js`, ~70 чипов с ориентировочным баллом Geekbench 6
single-core) и сохраняет всё в `settings.perf`. С этого момента у каждого эмуляторного замера есть
прогноз: p95 на эталоне = p95 с эмулятора × K, на другом чипе — пропорционально баллу, и две цифры
«нужен чип от N баллов» для «нормально» (p95 ≤ 12 мс) и «плавно» (≤ 7 мс). Чип не в таблице —
консоль спросит балл; свои чипы — `settings.perf.chips: [{ code, name, score }]`.

Калибровка запоминает, когда и на чём снята: образ эмулятора, обе сборки, p95 эмулятора. Прогноз показывается
числом только пока она годится для прогона. Вместо чисел консоль пишет причины, если калибровке больше
14 дней, её возраст или происхождение неизвестны (старая запись с одним K), она снята на другом образе
эмулятора, сравнивала разные сборки или варианты, K вне 0,1–3 или p95 сценария на эмуляторе ушёл больше чем
вдвое от калибровочного. Тогда калибровку надо снять заново. Прогноз старых прогонов пересчитывается по
текущей калибровке — её дата стоит в заголовке блока. Ответ калибровки (и CLI) сообщает `check` — будет ли
она давать прогнозы. Из командной строки: `node tools/e2e.js calibrate <id прогона на телефоне>`.

Оговорки по Flashlight: его fps считается по atrace и для простоя берётся за 60, поэтому «45 fps» у
Flashlight и 10 кадров на свайп в наших данных не противоречат друг другу — смотрите на стоимость кадра и
jank; его профайлер сам добавляет нагрузку (на перегруженном эмуляторе ~20 % к стоимости кадра), для
чистого сравнения сборок между собой выключайте его (`flashlight: false` или `--no-flashlight`) и
держите один режим во всей истории.

## Движки экрана

Экранные шаги выполняет один из трёх движков — выбор в настройках и у каждого сценария, разово:
`node tools/e2e.js run <id> --engine maestro`.

- **adb** — свой драйвер (uiautomator + `input`). Быстрее, умеет сдвиг от элемента и `count`. Ввод не-ASCII идёт
  через буфер обмена компьютера, поэтому работает на эмуляторе, который его зеркалит; на macOS нужен `pbcopy`,
  на Linux — `wl-copy` или `xclip`.
- **Maestro** — подряд идущие экранные шаги уходят одним flow (`data/runs/<id>/maestro/steps-N-M/flow.yaml`),
  отчёт раскладывается обратно по шагам. На iOS — единственный движок. Переменные прогона передаются Maestro
  через окружение (`MAESTRO_E2E_V*`), а не в командной строке: значения с `&`, `|`, `%` безопасны и не
  попадают в `flow.yaml`. Путь к Maestro CLI и серийный номер устройства не должны содержать `"` и `%`.
- **web** — страница в браузере через Playwright поверх уже установленного Chrome или Edge (`playwright-core`
  ставится вместе с консолью, браузер не скачивается). Те же шаги, что и на телефоне: «Открыть» открывает
  адрес (`url`, полный или путь от «Адреса сайта» в настройках), «Нажать» и «Проверить экран» ищут текст
  элементов, подпись поля, placeholder или aria-label, «Ввести» печатает в поле под курсором (для `<select>` —
  выбирает пункт по тексту), «Пролистать» крутит колесо, «Назад» — история. Перед нажатием элемент прокручивается
  в середину своей панели (страницы часто скроллят не окно, а внутренний контейнер, и кнопка у нижнего края
  оказалась бы под закреплённой панелью); элементы, которые страница отключила, шаг ждёт до `timeout`. Нажатие
  не проходит «сквозь»: если элемент скрыт, прозрачен, перекрыт другим или исчез со страницы после снимка, шаг
  падает с объяснением, а не кликает что придётся. `storage` у «Открыть» кладёт записи в localStorage до
  скриптов страницы (только для сайта из `url`, один раз) — готовая сессия, флаги; редирект при первой загрузке
  их не теряет. Язык страницы — настройка `web.locale` (пусто — язык системы). Запросы страницы (fetch/XHR) показываются на шаге как запросы приложения, правило
  `noServerErrors` их тоже считает. Без окна по умолчанию; в настройках можно включить видимое окно.

Чего у Maestro нет, консоль делает поверх при любом движке: проверки бэкенда от любых ролей, логи бэкенда
и замечания к запросам приложения, эталонные скриншоты, ручные шаги, макеты Figma, условия и повторы.
Шаги, которые Maestro не выражает, при движке Maestro выполняет adb.

### Телефон и браузер в одном сценарии

Экран можно задать для части шагов: группа `browser: [...]` выполняет вложенные шаги в браузере, `phone: [...]`
— на телефоне, `on: web` / `on: phone` переключает один шаг, условие `if` смотрит туда же (`on` внутри условия
переопределяет). Сценарий с `engine: web` целиком идёт в браузере и телефона не требует; сценарий с шагами на
обоих экранах берёт телефон, а браузер открывает на первом его шаге и закрывает в конце прогона.

```yaml
steps:
  - use: checkout          # телефон: покупатель оформляет заказ
  - browser:
      - launch: { url: /admin/orders, storage: { session: '{"accessToken":"{{buyer.token}}", …}' } }
      - input: { target: order_id, text: "{{orderId}}" }
      - tap: { target: Передать в доставку, timeout: 120 }
  - use: open-order                   # снова телефон
    with: { tab: Архив }
```

На странице прогона лента скриншотов делится на участки «телефон» / «браузер», кадры браузера широкие, а
открытый шаг браузера показывается окном с адресной строкой на всю ширину. Замер скорости шаги в браузере не
трогает: он про приложение.

## Вкладки списка

Список сценариев разложен по вкладкам. Из коробки их две — «Тесты» и «Нагрузка» (сценарии с `measure` или
тегом `perf`, с баллами вместо успешности), но вкладки свои: «+» рядом с ними создаёт новую, «✎» переименовывает
или удаляет текущую. Сценарий переносится селектором «Вкладка» в своей строке или в редакторе; в YAML это поле
`tab: <имя или id>`. Сценарий без `tab` ложится по своему типу — измеряемые в первую нагрузочную вкладку,
остальные в первую обычную. Вкладки хранятся в настройках (`tabs`) и уезжают в экспорт вместе с ними.

## Устройства и очередь

Подключённые устройства — adb (Android) и `xcrun simctl` (iOS-симуляторы, только macOS). Прогон ставится
в очередь и стартует на свободном устройстве: в шапке выбор «любое / конкретное / все сразу»
(`--device <serial>|all` в CLI). На разных устройствах прогоны идут параллельно, на одном — по очереди.
Очередь живёт в памяти консоли: после перезапуска ожидавшие и шедшие прогоны помечаются остановленными с
причиной — их надо запустить заново.
Для iOS в настройках нужен `bundleId`; известные устройства можно описать в `devices`
(`[{ serial, platform, name }]`). iOS-драйвер написан без Mac под рукой — проверь на первом запуске.

## Старые прогоны и скриншоты

Каждый прогон — своя папка в `data/runs`, новый запуск ничего не затирает, поэтому папка растёт
(скриншоты — почти весь её объём). Убирать лишнее можно тремя способами:

- **Режим хранения** — «Настройки → Правила прогона → Скриншоты старых прогонов» (`runs.screenshots`):
  `all` хранит всё (по умолчанию); `latest` — новый запуск сценария стирает скриншоты его прежних
  прогонов. Статусы, время шагов, логи и баллы замеров остаются, история и успешность не страдают.
  Запуск, который не начался (нет устройства), ничего не стирает.
- **«Удалить прогон»** на странице прогона — папка прогона целиком.
- **«Очистить»** над списком «Последние прогоны» — оставить по одному или по пять последних прогонов на
  сценарий, удалить старше недели, либо удалить только старые скриншоты. Перед удалением консоль
  показывает, сколько прогонов уйдёт и сколько места освободится. Замеры целиком не удаляются: у них
  уходят только скриншоты, чтобы не пропала история баллов. Идущие и ожидающие прогоны не трогаются.

То же по API: `DELETE /api/runs/<id>` и `POST /api/runs/prune` с телом
`{ keep, olderThanDays, what: "runs" | "screenshots", scenarioId, dryRun }`.

## Настройки, которые делают консоль «своей»

| Настройка | Что делает |
|---|---|
| `appName` | название в шапке |
| `package`, `activity`, `bundleId`, `avd`, `apkPath` | приложение и устройство |
| `apiBase` | адрес API для шагов «Проверить бэкенд» |
| `accounts` | роли с любыми именами: `{ buyer: { phone, otp, token }, seller: {…}, courier: {…} }` — токен вручную или через плагин входа. Переименование роли в таблице сохраняет её refresh-токен. Старые плоские ключи (`apiToken`, `sellerToken`, `refreshToken`…) при первом запуске один раз переезжают в `accounts` и удаляются из файла |
| `auth.plugin`, `auth.appAccount`, `autoToken` | плагин входа: JS-модуль с `freshToken()`, перед прогоном выдаёт свежие токены ролям (пример — `examples/auth-plugin.js`); `appAccount` — роль, под которой залогинено само приложение (для неё новый вход делают только сценарии с очисткой данных) |
| `templates` | именованные шаблоны: `{{context}}` в теле запроса → заданный JSON, `{{uuid}}`/`{{now}}` внутри новые на каждый вызов |
| `vars` | переменные `{{имя}}` для шагов |
| `appNet.tag` | тег logcat, куда приложение пишет свои HTTP-запросы; пусто — выключено |
| `logs.*` | логи бэкенда из VictoriaLogs в Kubernetes: `enabled`, `kubeconfig`, `namespace`, `service`, `port`, `filter` |
| `allowStatus`, `screenIgnore` | статусы, терпимые для `noServerErrors`; области экрана, которые эталон не сравнивает |
| `figmaToken` | показывать кадр макета рядом со скриншотом |

### Плагин входа

```js
// auth.plugin: путь от папки консоли или абсолютный; перечитывается на каждом прогоне
module.exports.freshToken = async ({ apiBase, role, phone, otp, refreshToken, allowMint, settings }) => {
  // ... вход или refresh для роли ...
  return { accessToken, refreshToken };   // refreshToken сохранится в accounts.<role> и придёт в следующий раз
};
```

Если новый вход выкинет приложение из того же аккаунта, плагин бросает ошибку с `code: 'MINT_NOT_ALLOWED'`
(и `hint` — текст для пользователя), когда `allowMint` ложно.

## Форматы: импорт и экспорт

Импорт — кнопка «Импорт» или `node tools/e2e.js import <файлы или папка> [--mode …] [--replace] [--dry]`.
Формат определяется сам:

| Формат | Что внутри |
|---|---|
| YAML / JSON консоли | сценарий, список шагов или пакет `kind: e2e-console/bundle` с `settings`, `secrets`, `scenarios` |
| Maestro flow | шапка `appId` + `---` + команды. Что консоль понимает — станет её шагами, остальное — шагами «Команды Maestro»; `runFlow: file` подставляется, `runScript`-файлы (.js) хранятся в шаге |
| `.env` | `APP_PACKAGE`, `BUNDLE_ID`, `API_BASE`, `AUTH_PLUGIN`, `APP_NET_TAG`, `FIGMA_TOKEN`, `<ROLE>_PHONE`, `<ROLE>_TOKEN`, `<ROLE>_REFRESH_TOKEN`, `ENGINE`, `MAESTRO_PATH`… — в настройки (`examples/keys.env.example`), остальное — в переменные. Пустые значения ничего не затирают |

Экспорт: у сценария — YAML консоли, JSON или Maestro (блоки раскрыты, условия — `runFlow.when`, повторы — `repeat`,
API-проверки — `scripts/*.js`, zip); на главной — все сценарии и настройки одним YAML, с ключами или без.

Что уезжает в пакет:

- **Без ключей** — только то, что имеет смысл на чужой машине: приложение (`package`, `activity`, `bundleId`),
  стенд и адрес API, движок, вкладки, шаблоны, правила прогона, названия ролей (без номеров и токенов),
  переменные, не похожие на личные, и библиотека блоков.
- **С ключами** — то же плюс токен Figma, роли целиком (номер, код, токен, refresh-токен) и личные переменные:
  те, чьё имя похоже на phone / otp / token / secret / password, и значения, похожие на номер телефона.
- **Ни в одном из двух** — пути этой машины (adb, эмулятор, APK, браузер, kubeconfig, Maestro, Java), AVD,
  серийные номера и список устройств, калибровка замеров. Экспорт с ключами — не резервная копия машины.

Блоки едут в пакете (`blocks:`): при экспорте всего — вся библиотека, при экспорте выбранных сценариев —
только блоки, которые они используют. При импорте блоки сливаются по имени: новый добавляется, одинаковый
пропускается, а отличающийся от твоего остаётся твоим, пока ты не выберешь «заменить» в предпросмотре
(`--replace` в CLI). Вкладки из пакета тоже добавляются к твоим, а не заменяют их.

В YAML-режиме редактора сохранение строгое: неизвестный ключ, непонятный шаг или комментарий — ошибка с номером
строки, и ничего не сохраняется (раньше такие строки молча пропадали). Сценарий хранится как данные, поэтому
комментарии сохранить нельзя — перенеси их в `description`.
Выгруженный Maestro flow идёт без консоли: `maestro test flow.yaml -e API_BASE=… -e BUYER_TOKEN=… -e COURIER_TOKEN=…`.

## Пресеты

Пресет — пакет `kind: e2e-console/bundle` (обычно без ключей) плюс плагин входа рядом; блоки едут в самом
пакете или отдельным файлом библиотеки. Сделать: «Настройки» → «Экспорт без ключей». Поставить: «Импорт» → файл, или

```bash
node tools/e2e.js import ../my-preset/preset.yaml ../my-preset/blocks --replace
```

Копировать блоки поверх `data/blocks/` не нужно: так затёрлась бы своя библиотека.

## Язык

Интерфейс на русском и английском: переключатель «EN / RU» в шапке, выбор хранится в браузере. Пока выбор не сделан, язык берётся из браузера: русский для русского браузера, иначе английский. Все
надписи интерфейса — в `public/i18n.js`: русский текст служит ключом, английский — значением; строка без
перевода остаётся русской, так что добавлять переводы можно постепенно.

Сервер говорит по-английски: названия шагов, детали, ошибки, замечания линтера, ответы API и вывод
`tools/e2e.js` — английские, и в `run.json` они лежат английскими, нейтральными к языку интерфейса. В
русском режиме интерфейс переводит их при показе по шаблонам из того же `i18n.js` (`tt()`); фраза без шаблона
показывается как есть. Прогоны, записанные до 2026-11-09 по-русски, читаются в обоих режимах: для них
оставлены обратные шаблоны. Модуль работает и в Node (`require('./public/i18n.js')`, язык из `E2E_LANG`),
если понадобится переводить вывод командной строки.

## Вторая консоль рядом

`node server.js --port 4778 --data data-bare` (или `PORT` / `E2E_DATA`) поднимает ещё одну консоль со своей папкой
данных. Пустая папка — это консоль «как из коробки»: без настроек, сценариев и блоков, так её видит человек без
ваших импортов. Папки `data*/` не коммитятся.

Одна папка данных — одна консоль: при старте консоль кладёт в неё `.console.lock` и не запустится, если папку уже
держит живая консоль (иначе две водили бы один телефон и гасили бы прогоны друг друга). Замок от упавшей консоли
снимается сам.

Копия настроек с включённым `autoToken` — это не «безопасная песочница»: она обновляет refresh-токены, и у
консоли, откуда настройки скопированы, они перестают работать. Для опытов на копии выключите `autoToken` или
перенесите свежие токены обратно.

## Безопасность

Консоль слушает только `127.0.0.1` и отвечает только на адреса `127.0.0.1` / `localhost` своего порта. Запросы к
API со страниц других сайтов (и других портов localhost) отклоняются по `Origin` / `Sec-Fetch-Site`, тело запроса —
только `application/json`. Командная строка и `curl` шлют запросы без `Origin` и проходят. Выставлять консоль в сеть
(через прокси или на общий сервер) нельзя: у неё нет входа, а настройки хранят токены и пути к программам, которые
она запускает.

`settings.json` и `run.json` пишутся атомарно (временный файл и переименование). Испорченный `settings.json`
консоль не перезаписывает: API отвечает ошибкой с причиной, файл надо поправить руками или восстановить.

## Как устроено

- `data/scenarios/*.json` — сценарии; `data/blocks/*.yaml` — общая библиотека блоков.
- `data/runs/<id>/` — прогон: `run.json`, `step-N.png`, `step-N.diff.png`, `logs.json`, `maestro/`.
- `data/baselines/<сценарий>/<имя>.png` — эталонные скриншоты.
- `data/settings.json` — настройки и ключи. Весь `data/` не коммитится.
- `lib/compile.js` раскрывает блоки, фазы, условия и матрицу в плоский список шагов; `lib/lint.js` проверяет его;
  `lib/runner.js` выполняет; `lib/maestro.js` и `lib/adb.js` — движки; `lib/ios.js` — simctl.
- `lib/perf.js` — замер: разбор `framestats` и `/proc`, статистика по кадрам, балл; `lib/flashlight.js` +
  `lib/flashlight-worker.js` — профайлер Flashlight в отдельном процессе и его отчёт. Результат — `perf` в
  `run.json` (по прогону) и `steps[].perf` (по шагам, с выборкой стоимости кадров для агрегации).

## Командная строка

```bash
node tools/e2e.js list
node tools/e2e.js lint all
node tools/e2e.js run login cart-add --engine maestro --device all   # код выхода 1, если что-то упало
node tools/e2e.js run perf-feed --measure --iterations 3           # с замером: балл, p95, jank, старт в выводе
node tools/e2e.js import examples/maestro --dry
node tools/e2e.js export cart-add --format maestro --out out/
node tools/e2e.js export all --out out/
```

Консоль по умолчанию — `http://127.0.0.1:4777`; другую задаёт `E2E_CONSOLE=http://127.0.0.1:4778`.
Флаги-переключатели (`--force`, `--measure`, `--no-flashlight`, `--replace`, `--dry`, `--secrets`) значения не
берут, поэтому их можно ставить где угодно; `run` без id сценария — ошибка (код 2).
